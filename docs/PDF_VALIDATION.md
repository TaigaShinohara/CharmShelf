# PDF runtime validation

The first post-publication priority is the PDF viewer introduced with pdfrx.
The source-preview publication is already complete; this work does not repeat
release preparation or establish signed-distribution readiness.

## Isolated native smoke test

`integration_test/pdf_viewer_smoke_test.dart` uses original, deterministic PDF
fixtures generated by `integration_test/support/pdf_fixture.dart`. They contain
two pages of English text, an external annotation targeting the reserved
`example.invalid` domain, and an internal page destination. The encrypted
variant uses PDF Standard security revision 2 with the public fixture password
`qa-reader`; it is test data, not a credential or recommended encryption format.

Use Flutter 3.47.9 and the normal setup guide. Create a **dedicated, empty iOS
Simulator or Android emulator** and check its ID before running the command.
Do not run this harness over an everyday app installation. The test does not
start `app.main`, open the library database, import files, or confirm URL launch.
It creates and removes only its own new temporary fixture directory.

An explicitly authorized physical-device run must use a fresh, separately
identified QA installation. On Android, the existing Gradle properties
`tagshelfPerformanceQa=true` and a new numbered `tagshelfQaInstance` provide
that separation. Check the actual APK application ID and the absence of that
package on the specified device before installation. Keep the ordinary app's
data, existing QA packages and screen protection intact.

```sh
flutter devices
flutter test integration_test/pdf_viewer_smoke_test.dart -d SIMULATOR_ID --no-pub --reporter expanded
```

For a host screenshot after zooming, add
`--dart-define=CHARMSHELF_PDF_QA_VISUAL_PAUSE=true`. After the fixed
`CHARMSHELF_PDF_QA_ZOOM_READY` log marker, the test holds the settled synthetic
viewer for 30 seconds, then continues. This mode is optional and uses the same
dedicated target and temporary data boundary.

On hosts needing isolated Flutter/JDK settings, prefix the Flutter arguments
with `python3 scripts/flutter_local.py` as described in the setup guide. Check
active builds, memory and disk first; run only one build at a time. The iOS
target uses Swift Package Manager, with no store signing or CocoaPods setup.

The assertions cover:

- Native document loading and the app's content-ready callback; a nonblank
  PDFium render and two-page text extraction.
- Zoom and selected-text retrieval through the viewer controller. These do
  not establish the usability of finger gestures or selection handles.
- The app's link callbacks with annotations decoded by PDFium: external
  confirmation/cancellation without launch, and internal navigation to page 2.
  Annotation hit testing and external-app handoff remain separate checks.
- The app's password-entry flow: incorrect-password feedback, correct entry
  followed by rendering, cancellation without content-ready, and retry with a
  fresh prompt. Switching the document or removing the reader closes its old
  prompt without affecting another route. New loads do not retain the input.
- Invalid-document failure, replacing only the synthetic fixture, retrying
  successfully, and preserving both original plain/encrypted fixture bytes.

Password entry is requested only when PDFium cannot open a PDF without one.
The input is obscured, with keyboard suggestions, personalized learning and
autofill disabled. Values are passed unchanged (including whitespace) to the
document loader and are not persisted or logged by the app. A cancelled load
returns to the existing retry/external-open/share panel. The UI is localized in
Japanese and English. This does not establish support for every PDF encryption
algorithm or document restriction; the native fixture uses revision 2 only.

## Recorded run

On 2026-11-03, the native smoke test passed on a newly created, dedicated
iPhone 17 / iOS 27.0 Simulator using Flutter 3.47.9 / Dart 3.13.7. The test
completed the initial smoke scenarios, before password-entry support was
added, including password-required and invalid-format failures followed by
successful document recovery. No app
database, personal files or physical device was used. This was one automated
integration test with multiple assertions, not a human touch-interaction review.
The optional settled-zoom checkpoint was also run successfully; its Simulator
screenshot was inspected separately from the moving/zooming frame capture.

The password-entry extension was subsequently checked on an explicitly
authorized Pixel 10 Pro / Android 17 (API 37) with a fresh isolated QA package.
The actual APK ID and the absence of that package were checked before install.
The full native test passed, including incorrect/correct input, cancellation
and retry, switching files, removing/reopening the reader, and original-file
hashes. Host coverage also passed (14 PDF/prompt/link tests), including English
large-text/keyboard layout and guarding against duplicate submit/navigation.
The same extended native test also passed on the dedicated iPhone 17 / iOS
27.0 Simulator. This includes document switching while a prompt is open and
closing/reopening the same encrypted file without retaining its input.
The Pixel uses 4KB pages, so it does not establish 16KB-device execution.
Android's existing `FLAG_SECURE` was retained. These automated assertions do
not establish human password-entry usability or full import-to-reader flows.

## Touch interaction corrections after physical QA

The 2026-11-03 physical review found that the enclosing media viewer could
claim PDF drags to dismiss the preview, and reported an internal link that did
not navigate. The initial correction disabled the enclosing dismiss and file-page
gestures. The file-routing correction below restores permitted horizontal file
swipes; vertical PDF dismissal remains disabled. Import previews have an
explicit close button in a reserved top area, including on devices without a
system Back button. It does not cover the document or selection endpoints.
Library viewers retain their close and file-position controls. PDF-classified content
taps control the toolbar; raw pointer-up observation no longer also handles
annotation taps.

The large triangular selection markers are replaced by 14dp round markers with
48dp finger targets. Password entry now offers localized show/hide controls,
starts obscured on every new prompt and preserves the input when toggling.

The extended native suite passed on the isolated Pixel 10 Pro installation.
It now includes the real media-preview screen, actual taps on external and
internal annotations, long-press word selection, dragging a selection endpoint
to extend the selected text without panning the PDF, scrolling the document and
dragging downward without moving or dismissing the preview. The password,
failure/recovery and original-file checks also passed. Related host coverage
passed (44 tests), including restoring toolbar access on a failed PDF,
closing an import preview without a swipe,
restoring normal image gestures after leaving a
PDF and retaining password privacy settings while toggling visibility.

These automated touch events are distinct from the owner's next review of the
updated markers and finger interaction on the retained manual QA app. The owner
confirmed the previous external-link and password-entry behavior; those flows
remain covered by regression checks.

## File swipes and link feedback

The owner subsequently confirmed scrolling, selection endpoints, internal links
and password visibility, but found that the first correction also disabled
swiping to the next file. A single-finger horizontal drag now uses the existing
file-page controller when a PDF fits its viewport width and has no selected
range. Permission is checked at pointer-down, not after the debounced selection
notification. Zoomed PDFs retain horizontal panning, selected ranges retain
their handles, and vertical scroll, long press and two-finger pinch remain with
the PDF. Loading and failure content can also be left with a file swipe.
The file controller retains the user's reading direction and page settling.

The horizontal recognizer is registered before the PDF pan recognizer while
preserving normal child hit testing. This covers coarse first-move events as well as
normal swipes, without letting a second pointer start file paging. Vertical
intent releases this recognizer at touch slop rather than delaying native pan.
The initial accepted move is preserved instead of consumed by recognition.
If a second finger joins an already accepted file drag, the file controller
returns to the starting file, even past the halfway point. The overlay owns
the additional pointer, including outside the moving PDF hit area, and forwards
both touches through pdfrx's public pan/zoom API, because the native PDF
recognizer has already lost the first touch's arena.
Viewport-local positions are rebased after the file snap to avoid shifting the
pinch pivot. Either finger can lift first; the remaining finger can keep panning.
Ordinary two-finger pinches continue through the native PDF recognizer. Unrelated
image and other media gestures retain their existing handling.

Link taps briefly strengthen the annotation fill and border and request a light
selection haptic through the existing user/feature-setting gate. Internal
navigation also shows the destination page position briefly. External links
still require confirmation, and cancelling never launches them. Link targets
and passwords are not added to logs.

Related host coverage passed (53 tests). The isolated Pixel native suite also
passed, including swiping forward and back between two PDF files, retaining
document interactions while zoomed or selected, a real two-finger pinch,
a late second finger after dragging beyond the file-page midpoint,
visible link-feedback pixels, destination-page feedback, and the existing
password/recovery/original-file checks. This extends the earlier single-file
gesture validation; the updated file-switching feel and haptics still need an
owner review on the retained QA installation.

## Remaining checks, in priority order

| Priority | Check | Environment / restart condition |
| --- | --- | --- |
| 1 | PDF touch zoom, long-press selection/handles, scroll and back navigation | Dedicated Android/iOS device or isolated app installation, identified before use; synthetic files first |
| 1 | PDF annotation hit testing, link cancellation/confirmed handoff, missing/unreadable files | Same target, with OS handoff observed; never use personal document links as fixtures |
| 1 | Password-entry usability, additional encryption formats and document restrictions | Automated coverage uses a synthetic revision-2 PDF; verify representative files and actual keyboard/gesture behavior separately |
| 2 | Background audio, interruption/resume, permissions, OS pickers and sharing | Confirm device, application ID, allowed permissions and synthetic media before operations |
| 2 | Backup and restoration, cancellation/partial failure, existing-data preservation | Disposable library and explicit source/destination; keep ordinary data and originals untouched |
| 3 | Linux, Windows, macOS and Web runtime | Separate available environment and scoped scenarios; project files alone are not runtime validation |
| Separate distribution work | Official signing, store purchases, uploads, store or signed-binary distribution | Requires a new explicit request and the distributor's own configuration; old TagShelf credentials are not reused |

Physical-device behavior, human review, Simulator assertions, build success
and distribution validation must be reported separately. The previous
source-snapshot checks remain recorded in [VALIDATION.md](VALIDATION.md).
